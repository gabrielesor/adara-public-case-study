# Order and Trading Lifecycle

Adara treats an order as a controlled lifecycle with retained provenance and decision context, not as a single API request.

## Sources of trading activity

Adara distinguishes at least three origins:

- **Discretionary** — human-directed activity created through Adara.
- **Automated strategy** — intent generated by a hosted strategy.
- **External** — activity created outside Adara and later synchronized or observed at the exchange.

The first two are Adara-originated and can follow the controlled pre-trade path. The third is visible history, not retroactive proof that Adara controlled the order before execution.

## Controlled path

At a high level:

**intent → validation → compliance → confirmation where applicable → exchange submission → monitoring/fills → retained lifecycle + decision context**

Validation establishes that the intended order has a coherent operating context.

Compliance then evaluates the applicable controls. If an enforced control fails, the order is stopped before the exchange boundary.

Human confirmation may apply to discretionary execution; automated strategy orders are not described as requiring individual human confirmation.

## Decision provenance by design

Order origin alone is not enough for historical explainability.

For Adara-originated activity, the persistence model is designed so that the order can remain associated with the operational context relevant at decision time, including:

- strategy or discretionary origin;
- account and portfolio state;
- normalized valuation/exposure context;
- strategy configuration/context where relevant;
- compliance evaluation and retained evidence; and
- subsequent execution/fill state.

The goal is practical reconstructability.

Years later, a reviewer should be able to ask:

- Why was this order considered compliant?
- What portfolio/account state was relevant?
- Was it discretionary, automated, or external?
- For an automated order, what retained context explains why the strategy acted?

This is stronger than merely keeping an exchange order identifier.

## Exchange submission and monitoring

After applicable validation, compliance, and confirmation, Adara submits the order to the external exchange.

The platform then tracks lifecycle and execution information such as open/closed state, fills, execution price, cancellation, and fees, while preserving the order's origin and relationship to retained evidence.

Externally originated exchange activity can be synchronized into the same historical view while retaining external provenance.

## Known V1 latency debt

The order path is one area where the production system accumulated technical debt.

Although the market-data path was designed for low-latency tick handling, V1 order creation evolved to perform some report-generation and notification side effects synchronously. Depending on the path, observed end-to-end order creation could reach approximately **2–8 seconds**.

In practical terms, work such as compliance-document generation, email delivery, and messaging notification became coupled too closely to the critical execution path.

The behavior is documented rather than hidden because it is an important V2 design input: fast execution should be separated from asynchronous evidence generation and notification wherever the control model allows it.

## Evidence and reporting

For successfully controlled Adara-originated orders, Adara can generate order-level compliance evidence in PDF form, distribute it by email, and retain it server-side.

Daily portfolio-level compliance reporting is a separate scheduled evidence path.

These artifacts complement, rather than replace, the underlying retained order and operational state.

## Public boundary

No real order identifiers, quantities, prices, fees, account codes, proprietary strategy rules, credentials, or private exchange endpoints are published.
